# v1.2.0 HUD development history and renderer-probe implications

- Date: 2026-09-20
- Branch: `research/renderer-optimization`
- Game: Tekken 6 USA (`ULUS10466`)

## Purpose

This report reconstructs the development order behind the released v1.2.0 AutoHUD plugin. It exists because the final hook map can be misleading when read without its history: the battle HUD was first forced into a centered PSP-safe area, then individual families were reclassified and recomposed, and only later was the fixed 20:9 result generalized into AutoHUD.

That distinction matters for renderer optimization. A packet signature observed while an intermediate plugin was installed is not automatically a stock-runtime signature, and a final v1.2.0 hook does not prove that the same family was identified at that location from a clean stock control.

The immediate conclusion is:

> The missing side-strip samples in the focused stock probe do not disprove the shared sprite route, but the old plugin-era observations are not a sufficient stock control either. The probe must label the runtime generation and the exact measurement stage before its data can justify moving HP into the final side/rank dispatcher.

No production code was changed as part of this reconstruction.

## Runtime generations

The development should be understood as four distinct runtime generations.

| Generation | Runtime | HUD behavior | What captures from it prove |
|---|---|---|---|
| A | Stock/no plugin | Original stretched fight HUD | Native call flow and native packet state only |
| B | Early fixed-20:9 safe-area plugin | Selected fight-HUD paths uniformly reduced into a centered 16:9 island | Ownership experiments and provisional safe-area behavior; not final anchoring |
| C | Refined fixed-20:9 EXP6 | HP spans side-to-center; side/rank families anchor outward; other battle families use semantic anchors | The validated visual target and family-specific fixed-ratio behavior |
| D | EXP17/released v1.2.0 AutoHUD | EXP6 behavior expressed with aspect-derived coefficients inside the compact resident layout | Final released behavior at the tested aspect, including dynamic HP coefficients |

Comparisons must not mix these generations without naming the difference. In particular, Generation B was already mutating packets at shared renderer calls while the remaining families were still being discovered.

## Chronological reconstruction

### 1. September 3: high-level HUD projection research began before a production plugin existed

The project began with a known-good 20:9 3D CWCheat. The 3D scene was correct, while HUD/UI remained horizontally stretched under PPSSPP Stretch.

The first research tried to find a high-level 2D equivalent to the proven 3D projection patch:

- direct orthographic setup paths;
- a Warriors-style separate HUD-scale architecture;
- descriptor/property setters;
- the native PSP 2D presentation and viewport path.

The isolated orthographic candidates did not move the visible HUD. Broader projection and common-sprite experiments caused pause/menu collateral, empty or malformed health fills, and other unrelated UI damage.

This established the first lasting rule: Tekken's HUD is not one homogeneous 2D layer.

Relevant reachable history begins with:

```text
f720d01  initialize research repository
5e2afbc  map known aspect-ratio patch sites
ac0324b  map projection-builder call paths
f47aed4  record no-op orthographic diagnostics
9b06fe9  study Warriors aspect and HUD architecture
13fbc2d  add experimental Tekken 6 ultrawide PRX
5b97913  trace native PSP 2D presentation path
ac8f67d  add native PSP 2D safe area
```

The early September 3 PRX work was experimental and was later removed when the repository temporarily refocused on CWCheats. It should not be confused with the later v1.1.0 or v1.2.0 release modules.

### 2. September 13: v1.1.0 established the automatic 3D plugin baseline

The next production plugin solved automatic 3D aspect correction by asking PPSSPP for the current display aspect and patching four Tekken projection instruction pairs:

0x08946BC8 / 0x08946BCC

This became v1.1.0. It corrected 3D automatically but did not yet correct the HUD.

Directly retained commits cover the EXP14/EXP15 diagnosis. The v1.2.0 HUD work started from this installed, functioning plugin foundation.

### 3. September 13: the first fight-HUD milestone was a centered PSP safe area

The first explicit fight-HUD objective was not the final native ultrawide composition. It was a controlled, fixed-20:9 proof:

```text
s = 0.8
x' = 0.8*x + 48
width' = 0.8*width
```

The goal was to move only the active fight HUD into a centered 16:9 island while leaving the 3D scene ultrawide and leaving unrelated menus alone.

The now-unreachable history preserves this stage in detail:

```text
0ef4553  document isolated fight HUD safe-area strategy
ce5ed57  add fight HUD path-mapping diagnostic
028a41f  map battle gauge class hierarchy
4e7fc92  add orthographic UI render-group mapper
d62aa73  add group 10 HP safe-area proof
9ed7e09  document PPSSPP frame-dump differential
cba1c62  add targeted HP shell ownership diagnostic
85dace1  confirm HP shell ownership on device
d542377  add scoped HP fill HUD hook
```

Two results from this stage are critical to interpreting later notes.

First, `0x0892D56C` and `0x0892D5B0` were used as a narrow diagnostic control because changing packet X at those calls visibly affected HP-related rendering. The early hook applied the centered transform directly to packet fields and then called `0x08825EAC`.

Second, the hook was broader than the final HP owner. Historical packet captures at this shared path included recurring shapes such as:

```text
x=38, y=56, 64x32
x=4,  y=22, 256x32
x=4,  y=6,  256x32
```

At that point these were candidates inside a shared renderer, not yet a complete final semantic classification. The installed safe-area hook could mutate their X/scale before the stock submitter saw them.

The centered-safe-area build was visually confirmed: health frames and colored fills moved together into the original PSP-safe region. This was retained as a rollback/reference implementation, not accepted as the desired final composition.

### 4. September 13–14: the design pivoted from “safe area” to semantic ultrawide composition

Once the centered proof worked, the project deliberately changed its goal. The active fight HUD should use the wider frame rather than remain inside a 16:9 island.

The new semantic model was:

```text
P1 information             -> LEFT
neutral/timer/round family -> CENTER
P2 information             -> RIGHT
long HP bars               -> SIDE_TO_CENTER
```

For 20:9:

```text
LEFT:   x' = 0.8*x
CENTER: x' = 0.8*x + 48
RIGHT:  x' = 0.8*x + 96
```

The deleted history records this pivot in:

```text
569c22c  document battle HUD anchoring overhaul
0cddc7b  add HP span runtime probe
fc2570c  record HP span probe v1.3 findings
5d8c794  revise battle HUD anchoring from clean probe
28e685a  preserve HUD implementation snapshot
```

This is the historical point emphasized by the project owner: the plugin had already produced a PSP-safe-area battle HUD before the remaining elements were re-probed and assigned their final anchors.

### 5. September 14: HP shell and fill were changed from centered-safe-area behavior to side-to-center span

The long HP shell was isolated with the exact slot-`0xEF` builder shape:

```text
a3=5
t0=256
t1=32
t2=256
t3=32
```

The fixed-20:9 result became:

```text
P1 shell: -21, width 256 -> -17, width 253 -> span -17..236
P2 shell: 501, width 256 -> 497, width 253 -> span 244..497
```

The colored HP fill was moved away from the shared downstream packet mutation and into the narrower gauge-owner calls:

```text
0x0892C1F0
0x0892C26C
    -> 0x08928FF4
    -> 0x0892D3E0
    -> 0x0892D56C / 0x0892D5B0
    -> 0x08825EAC
```

The fixed implementation copied the gauge coordinates into plugin scratch storage, shifted X by side, and scaled the live health width:

```text
P1 X += 1.3056111
P2 X -= 1.3056111
width *= 1.0493455
```

The move to the upstream gauge owner was not arbitrary. At the time it supplied proven side ownership and health-dependent width while avoiding cumulative mutation of the persistent gauge object.

The original and rebased milestone commits are:

```text
d451087 / 829b065  validate fixed 20:9 HP span
```

The `829b065` diff is especially important: it removes the old `0x0892D56C/5B0` “fill” installation and replaces it with the two upstream gauge-owner patches. This proves that the final upstream HP wrapper was created after the centered shared-path proof.

### 6. September 14: side strips/lightning and rank badges were corrected after the HP-span milestone

Only after the HP span passed did the project add a dedicated downstream shared-sprite dispatcher back at:

```text
0x0892D56C
0x0892D5B0
```

The first final-style predicates were:

```text
y=22, 256x32 -> translucent under-bar / lightning side-strip family
y=56, 64x32  -> rank-badge family
```

The two families required different side classifiers:

- Side strip/lightning used the orientation sign retained in the packet.
- Rank badges could use the same positive orientation on both sides, so authored X relative to 240 selected LEFT or RIGHT.

The implementation applied horizontal scale plus semantic side anchoring and forwarded to `0x08825EAC`.

The relevant original/rebased commits are:

```text
53851f9 / 9d03520  correct rank badge side anchoring
9f30125 / cadfa72  record battle HUD composition progress
```

This ordering answers the central historical question:

> Rank and lightning were not the basis of the first safe-area proof. They were remaining shared-path families corrected after HP had been moved to its side-to-center owner path.

The final v1.2.0 architecture therefore contains both an upstream HP hook and a downstream side/rank hook because those responsibilities emerged at different research stages.

### 7. September 14–15: round markers and winner glow proved that one semantic family can have multiple render paths

Persistent round markers used the centered rectangle family, but a newly earned marker could be submitted after the normal scope closed. The first P2 orb at authored X=273 exposed a one-pixel lower-bound mistake.

The transient winner glow was separate again: a rotated THROUGH-mode quad converted through `0x08AE94A4`, called at `0x08AC9C38`.

Important commits include:

```text
40cec77  correct late winner-orb submission
bf3afb4  include P2 first late-orb slot
9397dde  record neutral round-win findings
```

The lesson was architectural: semantic CENTER behavior can require more than one renderer hook.

### 8. September 15: the center timer exposed the hook ABI requirement

The large countdown used two calls to `0x0892D72C`:

```text
0x08929AF8
0x08929B44
```

The first wrapper made the timer disappear because it did not forward the original fifth stack argument. Preserving that argument restored the timer.

```text
9678006  add center timer scope wrapper
1aab8b2  preserve timer renderer stack argument
2f1a701  record validated center timer correction
```

This became a permanent rule for all later consolidation work: MIPS delay slots and stack arguments are part of the hook ABI.

### 9. September 15: character names required reclassification inside an existing compositor

Character-name art already traversed the slot-`0xEF` rectangle compositor. It was de-stretched by the existing transform but incorrectly CENTER-anchored.

The narrow authored family was:

```text
y=28
height=16
width=64 or 128
```

Authored X selected LEFT or RIGHT. No new text renderer hook was needed.

```text
3e3e180  record side-label capture findings
f847507  anchor character names by side
f111599  mark character names validated
```

The malformed v9/v9.1 artifacts also exposed the resident-module constraint. A clean rebuild retained the name fix while restoring replacement textures and normal fast-forward behavior.

### 10. September 15–17: Practice and Gold Rush required two text stages

Practice infinity was a separate sprite/rectangle path. Practice combo/damage rows and selected Gold Rush labels used a shared glyph family.

EXP2 and EXP3 proved that changing horizontal scale early at `0x08970A90` was required for true glyph de-stretch. EXP4 proved that later packed-state synchronization at `0x08970B24` was required for correct placement. EXP6 combined both.

```text
early stage: horizontal scale 100 -> 80
late stage:  packed scale synchronization
Gold late X: +120, so 0.8*(x+120) = 0.8*x+96
```

EXP6 became the accepted fixed-20:9 comparison checkpoint.

```text
a54c067  checkpoint fully corrected EXP6 HUD build
82b7352  preserve validated EXP6 artifacts
d9fe962  record final EXP6 scope and release handoff
```

### 11. September 16–17: resident PRX layout became part of runtime correctness

A controlled A/B changed only the mapped LOAD size:

```text
known good: p_filesz=0x0EB0, p_memsz=0x0EB0
bad test:   p_memsz=0x12D0
```

The larger resident mapping reproduced replacement texture/font regressions. The safe contract became:

```text
one PT_LOAD
p_filesz = 0x0EB0
p_memsz  = 0x0EB0
file size = 5626 bytes
```

This constraint explains why the release uses compact hand-integrated binary logic and why hook consolidation must recover code space instead of enlarging the module.

### 12. September 17–18: EXP6 was generalized to AutoHUD, then debugged downstream

AutoHUD derived its common horizontal coefficient from PPSSPP's runtime aspect:

```text
s = (16/9) / displayAspect
d = 1-s
```

It generalized LEFT/CENTER/RIGHT offsets, Q15 scale, font percentage, Gold source shift, and HP coefficients.

The HP functions recovered from the final binary were:

```text
hp_shift = 6.528055667877197 * d
hp_scale = 1.0 + 0.24672749638557434 * d
```

At 20:9 they reduce to the proven EXP6 constants.

Early AutoHUD builds lost the colored HP fill. EXP14 proved the upstream gauge hook still produced correct transformed values. Following the packet downstream found the actual fault: the compact side/rank hook had been shortened, but five rejection branches still targeted its old forwarding location. HP packets rejected the side/rank predicates and fell into NOP/import-stub space instead of reaching the stock submitter.

EXP15 restored one forwarding jump and recovered HP without changing HP math.

EXP16 then tried startup self-patching for dynamic HP, but reused initializer instructions that were still live for text/font setup. Practice, Gold Rush, and menu text disappeared.

EXP17 restarted from exact EXP15, preserved the initializer, and changed only coefficient transport so the upstream HP hook loaded already-computed dynamic values. It passed the final mode sweep and became v1.2.0.

## Final v1.2.0 family map

| Family | Proven owner/path | Final correction model | Why it remained separate |
|---|---|---|---|
| 3D scene | Four projection instruction pairs | Aspect-derived projection constant | Not a 2D HUD path |
| Long HP shell | Slot-`0xEF` rectangle construction | SIDE_TO_CENTER shell endpoints | THROUGH-mode authored geometry |
| Colored HP fill | `0x0892C1F0/26C -> 0x08928FF4 -> 0x0892D3E0` | Side shift plus live-width scale in scratch | Proven gauge side/width state was available upstream |
| Side strip/lightning | `0x0892D56C/5B0` shared sprite calls | LEFT/RIGHT from orientation | Shared path; filtered by Y and shape |
| Rank badge | Same shared sprite calls | LEFT/RIGHT from authored X | Orientation was not a reliable side discriminator |
| Round rail/persistent orb | Slot/rectangle compositor | CENTER | Existing scoped rectangle path |
| Immediate earned orb | Late rectangle submission | CENTER | Could arrive after normal scope closed |
| Winner glow | `0x08AE94A4` converter | CENTER on four source X values | Rotated THROUGH quad, not an ordinary rectangle |
| Decimal timer | Two calls to `0x0892D72C` | CENTER through scoped rectangle path | Separate owner and fifth stack argument |
| Character names | Existing rectangle compositor | LEFT/RIGHT from authored X | Classification fix, no new renderer needed |
| Practice/Gold glyphs | `0x08970A90` and `0x08970B24` | Early scale plus late state/placement synchronization | Geometry and placement were derived at different stages |

This table describes the final architecture, not the order in which ownership was discovered.

## What the historical side/rank captures actually prove

The old evidence proves all of the following:

1. Packets matching the `y=22, 256x32` and `y=56, 64x32` families reached the shared sprite region in the instrumented battle-HUD runtime.
2. Narrow family predicates at `0x0892D56C/5B0` could correct the visible side strip/lightning and rank placement without regressing the validated HP span.
3. Rank side ownership could be recovered from authored X when orientation was ambiguous.
4. The final plugin used those callsites as the side/rank dispatcher and HP packets also passed through it on their way to the stock submitter.

The old evidence does **not** independently prove:

1. that every historical packet dump was captured from completely stock/no-plugin memory;
2. that the old recorded X/scale values were always pre-hook rather than post-hook;
3. that the side strip is continuously submitted in every battle state;
4. that a zero-hit stock phase means the family uses another renderer;
5. that HP can be moved downstream without reproducing the exact released endpoints at full, partial, and low health.

## Reinterpretation of the September 20 focused stock probe

The first focused stock run produced useful facts:

- full HP captured P1/P2, resources `0x0D/0x0E`, X `205/275`, and width `191`;
- low P1 HP captured both resources with width about `35.017`;
- rank badges captured on both sides at the shared D56C path, resource `0x0C`, X `38/442`, width `64`;
- the side-strip phase captured no accepted packet;
- later quick sweeps captured no packets at all, including HP.

The rank result is direct stock evidence for the shared path. The side-strip zero is not equivalent evidence against it.

The later all-zero quick sweeps are primarily a debugger/probe reliability result, not a renderer result. HP was visibly present and had already been captured at the same sites, so a sweep that sees neither HP nor side/rank cannot be used to infer that those families stopped using the callsites. PPSSPP breakpoint/JIT re-arming must be fixed before repeating those phases.

The historical correction changes how the side-strip target should be described. `y=22, 256x32` is a final plugin-era family classification derived during the transition away from the centered safe-area build. It is a strong candidate filter, but the next clean stock run must re-establish its semantic identity instead of treating the label as an axiom.

## Why the current HP consolidation idea remains plausible

The stock census proved that HP packets at `0x0892D56C` still contain:

```text
X
Y=21
Z=1000
live health width
orientation/depletion direction
resource 0x0D or 0x0E
side/resource IDs 6/7/8/9
```

That is enough state to construct a strong HP predicate and to distinguish P1/P2 without reading the upstream gauge object.

The historical order also explains why this opportunity was not taken originally. The upstream wrapper was created when the gauge owner was the first location with proven side identity and live width. The downstream side/rank dispatcher was added afterward. The original implementation optimized for correctness under incomplete knowledge, not for the minimum final hook count.

This makes downstream consolidation a valid research question, but not yet a proven optimization.

## Required measurement model for the next A/B

Every sample should record these fields explicitly:

```text
runtimeGeneration:
  stock | safe-area-reference | exp6 | v120

measurementStage:
  pre-call-pre-delay
  callee-entry-post-delay
  final-submit

callsite:
  D56C | D5B0
```

This prevents three invalid comparisons:

1. stock pre-call state versus v1.2.0 post-wrapper state;
2. pre-delay stack/register state versus callee-entry state after a MIPS delay slot;
3. final v1.2.0 family behavior versus an intermediate centered-safe-area capture.

For `0x0892D56C` the delay slot is:

```text
0x0892D56C  jal   0x08825EAC
0x0892D570  swc1  f0,0x2C(sp)
```

The same logical stage must be compared in stock and v1.2.0.

## Revised probe protocol

Before any `OPT-EXP1` implementation:

1. Fix or work around PPSSPP breakpoint/JIT re-arm behavior. A phase that misses visible HP is invalid and should abort rather than wait for 15 seconds.
2. Use one short phase per fresh debugger attachment. The bot-controlled P2 makes long interactive phases unsuitable.
3. Capture the first complete HP frame immediately, then stop. Do not require the operator to hold approximate health percentages for a long window.
4. Capture stock and released v1.2.0 at the same callsite stage and preserve the paired JSON files unchanged.
5. Verify v1.2.0 by module identity plus released hook signatures; do not accept an ambiguous installed plugin.
6. Re-establish the stock `y=22, 256x32` semantic identity with packet/resource/caller evidence. Do not rely only on the historical family name.
7. Keep the successful stock rank samples as the initial negative-control family.
8. Collect non-target shared-path packets so proposed HP, side, and rank predicates can be tested for mutual exclusivity.
9. Compare visible endpoints, not only packet X and width. Derive each endpoint using the packet orientation and the actual renderer convention.
10. Validate full, partial, and low HP for both resources. P2 bot timing can be handled by accepting naturally occurring width bands instead of requiring exact percentages.

The existing uncommitted focused probe is experimental. Its successful JSON remains useful, but the tool should not be promoted as the authoritative A/B probe until it follows this protocol.

## Decision on `OPT-EXP1`

There is enough evidence to continue focused research, but not enough to implement `OPT-EXP1` yet.

Already proven:

- downstream HP identity survives in stock;
- P1/P2 and both HP resources are distinguishable;
- live width survives depletion;
- stock rank packets coexist at D56C and have a distinct predicate;
- the released downstream dispatcher already forwards rejected HP packets to the stock submitter.

Still required:

- matched released-v1.2.0 samples at the same measurement stage;
- exact stock-to-v1.2.0 X and width relationships across multiple widths and both sides;
- clean stock confirmation of the side-strip family;
- a mutually exclusive predicate audit against other shared-path traffic;
- endpoint-level numerical equivalence to the current upstream `hp_shift/hp_scale` result.

Only after those checks should the project decide whether these upstream components can be removed:

```text
0x0892C1F0 patch
0x0892C26C patch
upstream HP gauge wrapper
HP scratch-coordinate preparation
HP-specific coefficient loads in that wrapper
```

No byte-saving claim should be made until a real compact binary is built and measured.

## Contributor conclusions

1. The plugin history is a sequence of increasingly specific models, not one design implemented all at once.
2. The centered PSP-safe-area build came before the native ultrawide battle-HUD composition.
3. HP was moved upstream first because that was where side and live-width ownership had been proven.
4. Side strips/lightning and ranks were corrected later at the shared downstream callsites.
5. The final two-hook relationship is therefore historically contingent and may be consolidatable.
6. Historical plugin-era packet captures must not be presented as stock controls.
7. The first stock rank capture is valid evidence; the all-zero quick sweeps and missing side-strip phase are not negative renderer evidence.
8. The next task is a short, reliable, same-stage stock/v1.2.0 A/B—not an implementation.
9. The resident layout remains a hard compatibility constraint:

```text
one PT_LOAD
p_filesz = 0x0EB0
p_memsz  = 0x0EB0
```

10. The released v1.2.0 artifact remains authoritative until any optimized candidate reproduces its full behavior and passes the same texture/font, camera-cheat, gameplay-mode, and official-PPSSPP regression checks.
