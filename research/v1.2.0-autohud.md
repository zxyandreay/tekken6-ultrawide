# v1.2.0 AutoHUD research summary

## Goal

Extend the automatic 3D aspect correction from v1.1.0 so the persistent Tekken 6 fight HUD also adapts from the game's stock 16:9 logical presentation to PPSSPP's current landscape display aspect.

The release target is **Tekken 6 USA (`ULUS10466`)**.

## Aspect model

For a detected display aspect `A`, the AutoHUD work uses the stock logical base `B = 16/9` and horizontal scale:

```text
s = B / A
```

The general horizontal mapping is:

```text
LEFT:   x' = s*x
CENTER: x' = s*x + 240*(1-s)
RIGHT:  x' = s*x + 480*(1-s)

width' = s*width
```

At 16:9 this is identity. At exact 20:9 it produces the previously validated fixed values `s=0.8`, center offset `48`, and right offset `96`.

The HP-fill path uses aspect-derived shift/width coefficients generated during initialization rather than fixed 20:9 constants.

## Key research findings

### EXP6 established the visual reference

The fixed-20:9 EXP6 checkpoint established the intended battle-HUD presentation and validated:

- HP shell and fill alignment
- player-side HUD
- character names/ranks
- timer and round indicators
- Practice HUD
- Gold Rush labels
- winner effects
- custom replacement-texture/font compatibility

This was the visual reference for subsequent automatic-aspect work.

### Missing HP fill was a downstream control-flow bug

The AutoHUD experiments initially lost the colored HP fill. Restoring the old HP gauge math alone did not fix it.

Runtime tracing showed that a shortened side-strip hook retained stale rejection-branch destinations. HP packets took one of those branches, landed in the wrong fall-through region, and never reached the stock sprite-submission path.

The repaired build restores forwarding to the shared stock submission path. With that repair in place, both player HP fills submit normally again.

### EXP16 exposed an unsafe initializer reuse

An attempted startup self-patch reused initializer instructions thought to be dead. The HP fill remained visible, but Practice combo/hit text, Gold Rush labels, and some menu text disappeared.

That established that the reused initializer block still participated in font/text setup. The approach was rejected.

### EXP17 combined dynamic HP transport with the repaired path

The final validated candidate restarted from the repaired EXP15 baseline, left the initializer intact, and changed only the HP gauge coefficient transport so the gauge reads the already-computed dynamic HP shift and width scale.

That retained:

- the repaired HP submission path
- dynamic HP coefficients
- Practice combo/hit text
- Gold Rush `REWARD` and `ATTACK VARIATION`
- Arcade, Story, and Ghost Battle HUD behavior
- custom replacement-texture/font behavior
- the compact resident-memory footprint

## Memory/layout constraint

A recurring constraint during research was preserving the compact plugin layout used by the texture-safe builds.

The final validated PRX remains:

```text
file size: 5626 bytes
PT_LOAD p_filesz: 0x0EB0
PT_LOAD p_memsz:  0x0EB0
```

Increasing the resident footprint had previously correlated with replacement-texture/font regressions, so v1.2.0 preserves the validated compact layout.

## Device validation

The final candidate was tested across:

- Arcade
- Story
- Ghost Battle
- Practice
- Gold Rush

The test sweep confirmed the HP fill, mode-specific battle text, and replacement-texture/font behavior without the regressions seen in earlier AutoHUD experiments.

The implementation derives coefficients from PPSSPP's reported aspect at runtime rather than using a fixed 20:9 preset. The release test device used an approximately 20:9 presentation; other ratios were not independently device-tested during this cycle.

No experimental build name is included in the public archive.

## Source status

The v1.2.0 release is intentionally artifact-driven: the exact device-tested PRX is preserved and verified by checksum in the release pipeline.

The readable plugin source on `main` is not claimed to be byte-identical to the final AutoHUD binary. Future source reconciliation should reproduce the validated memory footprint, hook semantics, dynamic aspect behavior, mode-specific HUD behavior, and replacement-texture compatibility before replacing the authoritative release artifact.
