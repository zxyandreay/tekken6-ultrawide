# v1.2.0 AutoHUD reverse-engineering and implementation record

This document is the detailed engineering record for the Tekken 6 PPSSPP AutoHUD work that became v1.2.0.

It preserves the reverse-engineering evidence, failed experiments, implementation decisions, and validation results needed to understand how the final AutoHUD design was reached.

The release target is **Tekken 6 USA (`ULUS10466`)** running under PPSSPP in landscape orientation.

This is intentionally more detailed than the public release notes. It documents how the HUD was identified, which render paths were owned by which game systems, why several apparently reasonable approaches failed, how the fixed 20:9 EXP6 reference was produced, how the first AutoHUD attempts regressed HP fill, and how EXP17 became the final v1.2.0 release artifact.

No local network addresses, device identifiers, debugger endpoints, or workstation paths are recorded here.

> **Detailed archive:** See [`v1.2.0/README.md`](v1.2.0/README.md) for subsystem deep-dives, experiment-by-experiment build evidence, the HP packet-tracing record, and probe methodology.

---

## 1. Starting point: v1.1.0 already solved automatic 3D aspect correction

v1.1.0 had already established that the 3D scene could be corrected automatically by reading PPSSPP's current display aspect and patching Tekken 6's stock 16:9 projection constant.

The validated 3D projection instruction pairs are:

```text
0x08945F10 / 0x08945F14
0x08946794 / 0x08946798
0x08946BC8 / 0x08946BCC
0x08947D90 / 0x08947D94
```

The stock floating-point constant encoded there is the game's 16:9 projection value.

The v1.2.0 problem was different: most of the battle HUD is not positioned by the 3D projection. Large parts of the interface are submitted as screen-space or THROUGH-mode geometry. That means fixing the projection alone leaves HUD rectangles, bars, text, timer elements, and round indicators horizontally stretched or semantically mis-anchored.

The research therefore moved from a global projection problem to a **semantic 2D composition problem**.

---

## 2. The core HUD model

Tekken's original interface is authored for a 480-pixel-wide PSP logical screen with center at x=240.

The key idea developed during the HUD research was that not every element should simply be scaled from the left edge. Each element belongs to a semantic anchor family:

```text
P1 / left-side information   -> LEFT
neutral / center information -> CENTER
P2 / right-side information  -> RIGHT
long HP shells               -> SIDE_TO_CENTER / special span
```

For a display aspect `A`, with Tekken's logical base aspect `B = 16/9`:

```text
s = B / A
```

The general horizontal transforms are:

```text
LEFT:
x' = s*x

CENTER:
x' = s*x + 240*(1-s)

RIGHT:
x' = s*x + 480*(1-s)

width' = s*width
```

Vertical geometry is normally preserved.

At exact 20:9:

```text
s = 0.8

LEFT:   x' = 0.8*x
CENTER: x' = 0.8*x + 48
RIGHT:  x' = 0.8*x + 96
```

These fixed 20:9 values were first used to reverse-engineer and validate each HUD family before attempting automatic aspect generalization.

A recurring lesson was that **semantic ownership matters more than raw screen coordinates**. Two rectangles with similar size can belong to completely different HUD systems and require different anchoring.

# Part I — Building the fixed 20:9 reference

## 3. Why EXP6 mattered

Before attempting true AutoHUD, the research needed one build whose intended HUD behavior was already visually proven.

That became **EXP6**, the fixed-20:9 reference.

EXP6 was not the final automatic solution. Its purpose was to answer a more basic question:

> What should every important battle-HUD family look like when correctly composed for a wider display?

By the time EXP6 was accepted, the following were considered solved on the target device:

- automatic 3D ultrawide projection;
- long P1/P2 HP shells;
- both colored HP fill layers;
- side strips / lightning;
- rank badges;
- persistent and immediate round-win markers;
- winner glow;
- large center round timer;
- P1/P2 character-name anchoring;
- Practice infinite timer;
- Practice damage/combo readout;
- Gold Rush `REWARD` and `ATTACK VARIATION` labels;
- compatibility with custom replacement textures/fonts;
- compatibility with release camera CWCheats.

EXP6 therefore became the visual and behavioral reference that later AutoHUD experiments had to preserve.

---

## 4. Reverse-engineering the HP shell

### 4.1 GPU/frame-dump isolation

A differential analysis of PPSSPP frame dumps isolated the health-bar compositor.

The main shell family contained three central/background rectangles and four fill-related draws.

Important stock THROUGH-mode shell geometry included:

```text
center shell: 208..272, y=6..38
left shell:   -21..235, y=5..37
right shell:  245..501, y=5..37
```

The long side shells were especially important because they clearly demonstrated why the 3D projection patch could not fix the HUD: they were already submitted in screen coordinates.

### 4.2 Owner identification

The research traced shell ownership into `CMainTcb_t::Draw` around:

```text
0x0892BDAC
```

Slot `0xEF` was fetched and submitted in this path.

Suppressing only that slot removed the visible HP frames while leaving the colored fill layers, proving that shell and fill were separate rendering paths.

A clean rectangle census for the slot identified several shapes. The long shell pair had the stable authored signature:

```text
a3 = 5
t0 = 256
t1 = 32
t2 = 256
t3 = 32
```

### 4.3 Fixed 20:9 shell transform

The validated EXP6 shell endpoints were:

```text
P1:
stock x=-21, width=256
corrected x=-17, width=253
span -17..236

P2:
stock x=501, width=256
corrected x=497, width=253
span 244..497
```

The fact that the shell did not map perfectly through a generic 0.8 transform was one reason this family retained a narrow owner/shape-specific rule during the fixed-reference stage.

---

## 5. Reverse-engineering the HP fill

The colored HP fill was a separate and more subtle path.

### 5.1 Renderer path

Runtime work established the active fill path:

```text
gauge owner
    -> 0x08928FF4
    -> 0x0892D3E0
    -> 0x0892D56C
    -> stock sprite submission
```

The two gauge submissions were located at:

```text
0x0892C1F0   JAL path
0x0892C26C   tail-J path
```

Both eventually enter the original renderer at:

```text
0x08928FF4
```

### 5.2 Side ownership fields

Stable fields in the gauge object were identified:

```text
gauge + 0x5C:
0 = P1
1 = P2

gauge + 0x84:
+98.0 = P1 X source
-98.0 = P2 X source
```

At full health:

```text
f12 ~= 191.0
```

and depletion proportionally reduces that width input.

### 5.3 Why scratch coordinates were used

A first instinct would be to modify the live gauge object's coordinates directly.

That was rejected because the object persists and repeated mutation could accumulate over frames.

The validated implementation instead:

1. copies the source XY pair into plugin scratch storage;
2. applies a side-dependent X shift to the scratch copy;
3. points `t1` to that temporary pair;
4. scales `f12`;
5. enters the stock renderer.

For fixed 20:9, EXP6 used:

```text
P1 X shift = +1.3056111
P2 X shift = -1.3056111
HP width multiplier = 1.0493455
```

Both full and partially depleted HP were validated.

These constants later became central to the AutoHUD generalization problem.

---

## 6. Side strips and rank badges

A shared sprite path contained multiple visual families, so a global correction was unsafe.

Two useful packet signatures emerged:

```text
y=22, 256x32 -> side strip / lightning family
y=56, 64x32  -> rank badge family
```

The side strip retained useful orientation/side information.

The rank badge did not: both sides could share a positive orientation.

The final rank classifier instead used authored X relative to screen center:

```text
X < 240 -> P1 / LEFT
X > 240 -> P2 / RIGHT
```

Only horizontal position/scale were corrected.

This was an important general lesson: **when packet orientation is not semantically stable, authored position can be a safer ownership signal**.

---

## 7. Round markers and the first-win orb bug

Persistent round markers passed through the centered rectangle family.

However, the immediate newly earned marker could also arrive after the normal scoped path closed.

A narrow late-orb predicate was added for:

```text
y=27
16x16 authored rectangle
```

The first P2 win exposed a one-pixel classification bug.

The original P2 range began at `274`, but the first authored P2 orb was actually at `273`.

That caused the immediate first-win marker to miss the correction even though the persistent next-round marker was correct.

Changing the lower bound to `273` fixed the immediate marker.

This was a good example of why visually similar "same object" states can travel through different draw paths.

---

## 8. Winner glow: same semantic anchor, different renderer

The transient glow that appears around a newly earned round marker was not the same draw as the marker itself.

Frame captures isolated it as a rotated THROUGH-mode quad:

```text
4-vertex triangle strip
vertex type 0x80019E
64x64 texture
UV corners:
(0,0), (0,64), (64,0), (64,64)
```

Static correlation found the converter at:

```text
0x08AE94A4
```

called from:

```text
0x08AC9C38
```

The winner-glow hook therefore had to be separate from the ordinary rectangle compositor.

The useful result was conceptual:

> Different renderers can still share the same semantic CENTER mapping.

For fixed 20:9:

```text
x' = 0.8*x + 48
```

was correct for the glow as well as the round marker, even though the hook mechanism was completely different.

---

## 9. Center round timer and the ABI mistake

The large two-digit round countdown was another independent owner family.

Dedicated timer calls were identified at:

```text
0x08929AF8
0x08929B44
```

with the original timer renderer at:

```text
0x0892D72C
```

Authored positions were approximately:

```text
digit 1: x=211, y=7
digit 2: x=236, y=7
```

The timer belongs to the CENTER family.

The chosen implementation temporarily entered the existing centered rectangle scope while the original timer renderer executed.

### 9.1 The disappearing-timer failure

An early wrapper caused the countdown to disappear.

The bug was not geometry.

The original renderer consumes a fifth stack argument. The wrapper created its own stack frame but failed to forward that argument into the outgoing call frame.

Once the fifth argument was preserved, the timer rendered correctly again.

This became one of the project's most important low-level rules:

> MIPS hook correctness is not only about registers visible at the callsite; stack-passed arguments and delay-slot semantics must also be preserved.

---

## 10. Character names: classification, not a new renderer

Arcade/Story/Ghost captures showed character-name rectangles already passed through the rectangle compositor.

Before the side fix, they were horizontally de-stretched but incorrectly treated as CENTER-owned.

The stable authored family was:

```text
y=28
height=16
width=64 or 128
```

Recovered authored examples included left-side names near the left edge and right-side names near the right edge.

The fix was therefore not another renderer hook.

It was a semantic classifier:

```text
X < 240 -> LEFT
X > 240 -> RIGHT
```

while retaining the existing horizontal scale.

### 10.1 The contaminated v9/v9.1 experiment

An intermediate binary that included the name-anchor change also enlarged the PRX LOAD segment.

It produced unrelated problems:

- some replacement textures stopped being selected;
- fast-forward behavior regressed.

A clean rebuild from the known-good compact module layout retained the name fix while restoring those unrelated behaviors.

That established that the regression was **module-layout contamination**, not a flaw in the name classifier.

This finding later became crucial to the v1.2.0 release architecture.

# Part II — Mode-specific HUD reverse engineering

## 11. Practice infinity is not the normal timer

Practice mode's infinite-time symbol does not use the ordinary decimal timer path.

A stable post-transform signature was isolated:

```text
x=166
y=6
width=51
height=32
```

The device-proven correction changed only:

```text
x: 166 -> 214
```

with width/height unchanged.

This centered the infinity symbol around the logical screen center without touching the ordinary round timer.

---

## 12. Practice combo/damage text

The Practice statistics panel belongs to a shared font family rather than the rectangle path.

Target rows were identified around:

```text
y=104..116
y=116..128
y=127..139
```

The relevant left-side text needed a horizontal 80% scale for fixed 20:9.

The key discovery was that **where** the scale was applied mattered.

Changing only a late packed scale did not fully de-stretch glyph spacing because Tekken had already derived geometry from the earlier 100% scale.

This led to the early-vs-late experiment series.

---

## 13. Gold Rush labels and why one stage was not enough

Gold Rush contained several visually related but semantically different text families:

```text
REWARD
reward amount / currency
ATTACK VARIATION
floating +gold rows
mode/header text
```

Only two were targeted:

```text
REWARD
ATTACK VARIATION
```

The reward amount/currency and floating gold values remained stock.

The desired right-anchor transform at 20:9 was:

```text
x' = 0.8*x + 96
```

which can also be expressed as:

```text
0.8 * (x + 120)
```

That equivalence became useful when working inside Tekken's own font scaling pipeline.

---

## 14. EXP2 -> EXP6 mode-font progression

### EXP2 — correct early scale, incomplete mode integration

The correction moved to the earlier horizontal-scale path around:

```text
0x08970A90
```

Target glyph horizontal scale changed:

```text
100 -> 80
```

Result:

- Practice/Gold target text visibly de-stretched;
- Practice infinity still wrong.

### EXP3 — true de-stretch + correct infinity

EXP3 retained the early 80% scaling and corrected Practice infinity.

Result:

- Practice text de-stretched;
- Practice infinity correct;
- Gold text de-stretched;
- Gold placement wrong.

### EXP4 — later scale synchronization

The intervention was moved later around:

```text
0x08970B24
```

This improved state consistency and Gold placement.

But visual A/B showed the target text itself still looked stretched.

Reason: some glyph geometry had already been calculated from the original 100% scale.

### EXP5 — minimal fallback

Mode-font correction was removed, retaining only the Practice infinity fix.

This established a clean fallback within the safe memory footprint.

### EXP6 — dual-stage solution

EXP6 combined both useful ideas.

#### Stage 1: early true de-stretch

At:

```text
0x08970A90
```

target glyphs use:

```text
horizontal scale 100 -> 80
```

before downstream geometry derivation.

#### Stage 2: late packed-state synchronization

At:

```text
0x08970B24
```

the same target glyphs have their packed scale synchronized.

Practice authored X is unchanged.

Gold authored X receives:

```text
+120
```

so that:

```text
0.8 * (x + 120)
= 0.8*x + 96
```

This produced:

- visibly correct Practice de-stretch;
- correct Practice infinity;
- visibly correct Gold de-stretch;
- correct Gold right anchoring.

EXP6 therefore closed the fixed-20:9 HUD reference stage.

# Part III — The compact-memory constraint

## 15. Why PRX size/layout became a functional requirement

One of the most surprising findings was that module layout affected replacement textures/fonts.

A controlled A/B changed only the resident LOAD size:

```text
known-good:
p_memsz = 0x0EB0

expanded test:
p_memsz = 0x12D0
```

The larger mapping reproduced custom font/text replacement-texture regressions even without a meaningful corresponding HUD logic change.

Another contaminated experiment similarly grew the module and caused unrelated emulator/game behavior changes.

From then on, the accepted rule was:

```text
one PT_LOAD
p_filesz = 0x0EB0
p_memsz  = 0x0EB0
file size 5626 bytes
```

This meant "cleaner" source-level designs that required a larger module were not automatically acceptable.

The validated binary layout itself became part of the compatibility contract.

# Part IV — Generalizing EXP6 into AutoHUD

## 16. Why fixed 20:9 was only an intermediate milestone

EXP6 looked correct, but many of its values were explicitly 20:9-specific:

```text
horizontal scale = 0.8
center offset    = 48
right offset     = 96
Gold source shift= 120
HP shift         = +/-1.3056111
HP width scale   = 1.0493455
```

The real v1.2.0 objective was:

> Preserve EXP6's visual behavior while deriving those values from PPSSPP's detected aspect.

---

## 17. General AutoHUD equations

Let:

```text
A = PPSSPP-reported landscape aspect
B = 16/9
s = B/A
d = 1-s
```

Then:

```text
LEFT x        = s*x
CENTER x      = s*x + 240*d
RIGHT x       = s*x + 480*d
width         = s*width
Q15 scale     = round(s*32768)
font percent  = round(100*s)
```

For Gold RIGHT anchoring:

```text
gold_source_shift = round((480*d)/s)
```

because:

```text
s * (x + gold_source_shift)
~= s*x + 480*d
```

At 20:9, this becomes the fixed EXP6 `+120` source adjustment.

### 17.1 Recovered HP equations

The AutoHUD initializer also computed dynamic HP coefficients.

From the binary:

```text
hp_shift = 6.528055667877197 * d
hp_scale = 1.0 + 0.24672749638557434 * d
```

At 16:9:

```text
hp_shift = 0
hp_scale = 1
```

At exact 20:9:

```text
hp_shift = 1.3056111
hp_scale = 1.0493455
```

So the fixed EXP6 values were not arbitrary—they were the 20:9 instance of a continuous aspect-derived function.

Example values:

| aspect | s | center offset | right offset | HP shift | HP scale |
|---|---:|---:|---:|---:|---:|
| 16:9 | 1.000000 | 0.000 | 0.000 | 0.000000 | 1.000000 |
| 19.5:9 | 0.820513 | 43.077 | 86.154 | 1.171702 | 1.044284 |
| 20:9 | 0.800000 | 48.000 | 96.000 | 1.305611 | 1.049345 |
| 21:9 | 0.761905 | 57.143 | 114.286 | 1.554299 | 1.058745 |
| 32:9 | 0.500000 | 120.000 | 240.000 | 3.264028 | 1.123364 |

This established the mathematical basis for a true AutoHUD implementation.

# Part V — AutoHUD regressions and the missing HP fill

## 18. EXP11–EXP14: most dynamic behavior returned, HP fill did not

The early AutoHUD experiments introduced several regressions at once:

- replacement font/label textures stopped working in some paths;
- mode-specific HUD behavior regressed;
- HP fill disappeared.

By EXP11–EXP13, most font/mode behavior had been recovered.

The persistent failure was the colored HP fill.

Known milestones:

### EXP11

Recovered most mode/font behavior and the Gold Rush path.

HP fill still missing.

### EXP12

Changed dynamic HP coefficient transport.

HP fill still missing.

### EXP13

Changed coefficient transport/storage again.

HP fill still missing.

### EXP14

To isolate the issue, the working EXP6 HP gauge-hook implementation was restored into the AutoHUD build.

HP fill **still** remained missing.

That was a major clue.

It proved that the obvious gauge-math implementation difference was not sufficient to explain the failure.

The investigation had to move downstream.

---

## 19. Why static inspection was no longer enough

At this point several hypotheses remained plausible:

1. gauge owner site not actually patched;
2. wrong relocation target;
3. side discriminator no longer valid;
4. scratch pointer invalid;
5. renderer inputs differ despite similar source code;
6. inputs match but downstream packet/submission behavior differs.

A targeted runtime comparison between working EXP6 and broken EXP14 was designed.

The important methodological rule was:

> Compare the first causally meaningful divergence, not the first register value that looks different.

---

## 20. Debugger lessons that affected the investigation

Several low-level debugger details mattered.

### 20.1 JAL delay-slot semantics

At:

```text
0x0892C1F0
```

the JAL owner's delay slot performs:

```text
move t1,s0
```

Therefore raw `t1` observed before the JAL can be stale.

The effective hook input is the post-delay-slot value from `s0`.

The JAL-generated return address is:

```text
0x0892C1F8
```

not the incoming caller RA seen before execution.

### 20.2 Tail-J delay slot

At:

```text
0x0892C26C
```

the delay slot performs:

```text
addiu sp,sp,0x20
```

So downstream pairing must account for the changed stack pointer.

### 20.3 JIT-aware instruction reads

Raw memory reads could show JIT bookkeeping rather than the original instruction stream.

The investigation therefore used PPSSPP's disassembly path when validating live code flow.

This avoided false conclusions such as "the hook was overwritten" based on raw JIT-modified words.

---

## 21. EXP14 actually reached the HP renderer correctly

The first successful EXP14 full-HP capture showed that the supposedly broken build did, in fact:

- execute the HP hook;
- identify both sides;
- copy XY into scratch;
- apply the expected fixed EXP6 shift;
- scale `f12`;
- enter `0x08928FF4`.

Representative transformed values:

```text
P1 source X: +98
renderer X:  +99.3056107

P2 source X: -98
renderer X:  -99.3056107

f12:
191 -> about 200.424988
```

A transient reduced-width Practice capture also showed smaller HP widths traversing the same path.

This rejected several earlier hypotheses:

- hook not installed;
- bad side discriminator;
- missing scratch transform;
- width math never executed.

The missing fill had to be later.

---

## 22. EXP6 downstream baseline

The next probe followed a working EXP6 call farther downstream.

The observed renderer flow was:

```text
0x08928FF4   renderer entry
0x08929064   lookup call
0x0892906C   lookup return
0x089290B0   packet-builder call
0x0892D56C   final packet-builder submission call
0x08825EAC   stock sprite submission
0x089290B8   renderer return
```

For the four HP paths (P1/P2, layers 13/14), working EXP6 produced valid packets with approximately:

```text
P1 packet X: 206.305603
P2 packet X: 273.694397
Y:            21
Z:            1000
width:        ~200.425
height:       32
flags:        0xEA1
```

The stock submitter returned:

```text
v0 = 1
```

for all four paths.

Texture lookup and metadata were also valid.

That gave a concrete baseline for broken EXP14.

---

## 23. The actual HP-fill root cause: stale rejection branches

The first causally meaningful divergence was finally found in the downstream side-strip hook.

The AutoHUD rewrite had shortened this hook by eight bytes.

However, five existing rejection branches still targeted the old common forwarding location.

HP packets intentionally reject from the side-strip/rank-specific logic because their packet Y is:

```text
21
```

while that family expects other Y signatures.

In EXP6, rejection landed on a forwarding jump into the stock sprite submitter.

In EXP14, the shortened hook had moved the normal forwarding jump, but the old rejection destination had become NOP space.

The branch therefore fell through into the following import stub instead of submitting the HP sprite.

The important comparison:

```text
EXP6 old common bypass:
J 0x08825EAC

EXP14 same branch destination:
NOP
NOP
next import stub...
```

All five rejection branches still pointed to that old location.

The unintended import-stub execution also explained misleading secondary symptoms:

- caller-saved registers became junk/sentinel values;
- malformed log strings appeared;
- renderer return values differed.

Those were effects of falling into the wrong code, not causes of the missing fill.

This was the key AutoHUD debugging breakthrough.

---

## 24. EXP15: one-word control-flow repair

Once the stale bypass was proven, the next candidate changed exactly one aligned instruction word.

At PRX virtual address:

```text
0x092C
```

the candidate restored:

```text
J 0x08825EAC
```

The shortened hook's normal forwarding path remained intact.

No HP coefficients changed.

No branch displacements changed.

No LOAD size changed.

The PRX remained:

```text
5626 bytes
one PT_LOAD
p_filesz = p_memsz = 0x0EB0
```

### 24.1 EXP15 validation

The operator reported the colored HP fill was restored.

A follow-up runtime capture confirmed both players and both HP layers reached stock submission and returned:

```text
v0 = 1
```

This closed the missing-fill regression.

But EXP15 was not yet a true arbitrary-aspect HP solution.

Its gauge hook still embedded the fixed EXP6 values:

```text
shift = +/-1.3056111
scale = 1.0493455
```

Meanwhile the AutoHUD initializer was already computing dynamic values.

So the next problem became:

> How do we connect the dynamic HP coefficients without reintroducing regressions?

---

# Part VI — From repaired HP to true dynamic HP

## 25. The first generalization idea: startup self-patching

A reasonable architecture appeared to be:

1. preserve the proven EXP6-shaped hot hook;
2. calculate coefficients once during initialization;
3. patch the hook's embedded float immediates;
4. avoid adding runtime loads;
5. preserve the compact module layout.

This was attractive because earlier AutoHUD experiments that changed hot-hook code size/register usage had already caused control-flow problems.

The planned dynamic HP values were:

```text
hp_shift
hp_scale
```

computed from the detected aspect.

This became EXP16.

---

## 26. EXP16: mathematically correct idea, unsafe instruction reuse

EXP16 kept the repaired EXP15 HP submission path and changed startup initialization so it rewrote the immediate fields of the gauge's fixed HP constants.

The implementation used the initializer's live return address as a relocation-safe anchor.

The HP fill remained visible and the game did not crash.

At first glance, that seemed promising.

But device testing exposed new regressions:

- Practice combo/hit text disappeared;
- Gold Rush `REWARD` disappeared;
- Gold Rush `ATTACK VARIATION` disappeared;
- some main-menu text disappeared.

The conclusion was immediate:

> The initializer instructions reused by EXP16 were not actually dead.

They were still part of font/text setup.

The self-patching concept itself was not disproven, but this specific implementation destroyed unrelated state that EXP15/EXP6 depended on.

EXP16 was rejected.

---

## 27. EXP17: preserve initializer, change only coefficient transport

EXP17 restarted from exact EXP15—not from EXP16.

This was important because it restored the known-good initializer byte-for-byte.

EXP15 already calculated and stored:

```text
dynamic HP shift
dynamic HP width scale
```

EXP17 changed only six words in the gauge hook so the hot path loaded those already-computed values rather than embedding the fixed 20:9 constants.

Conceptually:

```text
fixed immediate shift
    ->
load dynamic hp_shift

fixed immediate scale
    ->
load dynamic hp_scale
```

The rest of the gauge behavior remained the proven EXP6/EXP15 shape:

- side identification unchanged;
- scratch XY unchanged;
- renderer forwarding unchanged;
- repaired downstream submission unchanged;
- initializer unchanged;
- module footprint unchanged.

This deliberately revisited the dynamic-load idea from earlier experiments, but with one critical difference:

> The stale side-hook forwarding bug was now known and already repaired.

That allowed the project to separate "dynamic coefficient transport" from the unrelated missing-fill control-flow fault that had previously confused the diagnosis.

---

# Part VII — Final validation

## 28. EXP17 result

EXP17 was tested across the important gameplay modes:

- Arcade;
- Story;
- Ghost Battle;
- Practice;
- Gold Rush.

The operator confirmed:

- HP fill present;
- full/partial HP behavior normal;
- Practice combo/hit/damage text restored;
- Practice infinity retained;
- Gold Rush `REWARD` restored;
- Gold Rush `ATTACK VARIATION` restored;
- main-menu text no longer disappeared;
- custom replacement textures/fonts still worked;
- no crash in the tested sweep.

This made EXP17 the first AutoHUD candidate that combined:

1. the complete validated EXP6-style battle HUD behavior;
2. the EXP15 downstream HP submission repair;
3. dynamic HP coefficient consumption;
4. the compact texture-safe resident footprint.

The release PRX SHA-256 is:


## 29. Why this qualifies as AutoHUD

The release is not a table of hardcoded 16:9 / 19.5:9 / 20:9 / 21:9 presets.

The HUD initializer derives its horizontal correction from PPSSPP's reported runtime aspect.

The general model returns to identity at 16:9 and continuously changes as the display widens.

That is fundamentally different from EXP6, which was a fixed 20:9 implementation.

The final release was visually validated on an approximately 20:9 target device because multiple physical aspect-ratio devices were not available.

Therefore the accurate claim is:

- the implementation is **aspect-derived / automatic**;
- the release behavior was **device-tested at the available target aspect**;
- every possible aspect ratio was not independently visually validated.

# Part VIII — Rejected approaches and what they taught us

## 30. Global/common sprite transforms

Rejected because they moved unrelated menus and UI.

Lesson:

> Patch semantic owners, not globally shared render primitives.

---

## 31. Global orthographic/projection changes for 2D

Rejected because many HUD elements are submitted as THROUGH-mode screen-space vertices.

Lesson:

> A correct 3D projection does not imply a correct 2D HUD.

---

## 32. Static descriptor writes

Some plausible structures were copied or relocated before the modified value mattered.

Lesson:

> Mutating a descriptor is useful only if the actual downstream owner still consumes that instance.

---

## 33. Long-lived breakpoints in hot render paths

They caused severe stalls or flashing and could distort the very behavior being observed.

Lesson:

> Use narrow conditional captures and short call-pair tracing.

---

## 34. Raw hit counts as semantic ownership

Rejected because a frequently hit renderer may service unrelated HUD families.

Lesson:

> Geometry, resource identity, caller context, side fields, and authored coordinates are stronger evidence than count alone.

---

## 35. Treating packet-local fields as universal pixel width

Some values initially looked like widths but behaved as scale coefficients.

Lesson:

> Validate field semantics through controlled changes and downstream packet geometry.

---

## 36. Assuming mirrored/world-matrix side from packet X

Rejected for some paths because local packet X can be mirrored or transformed.

Lesson:

> Side ownership may require a stable object field, authored pre-transform X, orientation, or caller identity depending on the renderer.

---

## 37. Enlarging the PRX to simplify implementation

Rejected after replacement-texture/font regressions.

Lesson:

> Binary memory footprint is a functional compatibility constraint, not merely a packaging detail.

---

## 38. Assuming source-level equality means runtime equality

EXP14 restored the visible EXP6 gauge-hook logic yet HP remained missing.

Lesson:

> A hook can be individually correct while a later shared path prevents the draw from reaching stock submission.

This is why the EXP14→EXP15 investigation followed the packet all the way to the final submitter.

---

## 39. Reusing "apparently dead" initialization code

EXP16 disproved this assumption.

Lesson:

> In a hand-integrated compact binary, code that appears unrelated to the current target may still feed another subsystem indirectly.

# Part XII — Research methodology

The process converged when experiments followed a strict pattern:

1. **Identify ownership first.**
2. **Use frame dumps to isolate geometry.**
3. **Correlate GPU draw families with CPU callers.**
4. **Prefer narrow predicates over global render hooks.**
5. **Preserve MIPS delay-slot and stack ABI behavior.**
6. **Keep the module layout byte/footprint-stable whenever possible.**
7. **Compare working and broken builds at the same render stage.**
8. **Follow the packet downstream until the first causal divergence.**
9. **Change one thing per candidate whenever possible.**
10. **Validate on the official emulator build before promoting a checkpoint.**

The EXP14→EXP15 result is the clearest example: once the investigation stopped changing HP math and instead followed the same packet downstream, the real one-word control-flow defect became obvious.

# Part XIII — Final synthesis


v1.2.0 was not produced by simply applying `0.8` to the HUD.

The final implementation grew out of a sequence of renderer-ownership discoveries:

- screen-space shell geometry;
- separate HP fill ownership;
- side-specific strip/rank semantics;
- persistent versus immediate round markers;
- a separate rotated winner-glow converter;
- timer ABI preservation;
- side-classified character-name rectangles;
- early versus late font scaling;
- strict compact-memory constraints;
- runtime packet tracing through the final sprite submitter;
- and finally dynamic coefficient consumption on top of the repaired draw path.

EXP6 established **what correct widescreen battle HUD behavior should look like**.

EXP15 established **why the AutoHUD HP fill was disappearing**.

EXP16 established **which initializer state could not safely be repurposed**.

EXP17 established **how to keep the repaired renderer path while actually consuming aspect-derived HP coefficients without regressing the rest of the HUD**.

That sequence is the real technical history behind v1.2.0.
