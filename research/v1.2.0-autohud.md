# v1.2.0 HUD correction and AutoHUD research

This is the end-to-end engineering record for the HUD-correction work that became v1.2.0.

The research starts from the known-good 3D-only state and follows each hypothesis until the final AutoHUD implementation.

The early projection, screen-space, and native-2D work is documented in `v1.2.0/origin-and-early-research.md`.

## 1. Actual starting state

The research started with a known-good 20:9 3D-only CWCheat for Tekken 6 USA.

At that point the 3D scene could be widened correctly, HUD/UI was still stretched under PPSSPP Stretch, no HUD transform was known, and no plugin existed.

Previous sprite-level experiments had already shown that broad 2D manipulation could break pause overlays, health fills, and other UI.

The original problem was therefore to find where Tekken converts logical HUD/screen-space coordinates into rendered output and correct only the appropriate paths.

## 2. High-level hypotheses were tested first

The research first mapped the known 3D projection sites and identified generic perspective and orthographic builders.

A centered 16:9 safe-area model inside 20:9 was mathematically sound, but the three direct 480x272 orthographic paths produced no visible HUD/UI/menu change when tested independently.

That negative result forced a pivot.

The project then studied separate HUD-scale architecture, ranked Tekken functions that looked like 2D scale/descriptor paths, and built runtime probes around candidate setters and native 2D presentation code.

The plugin/runtime mechanism itself also had to be debugged before HUD results could be trusted, including PPSSPP JIT/cache-order behavior.

Detailed evidence: v1.2.0/origin-and-early-research.md.

## 3. The research narrowed from global transforms to ownership mapping

After high-level projection/descriptor hypotheses failed to provide a complete HUD solution, the research switched to controlled battle-HUD diagnostics.

A +32-X path-map test established a known HP-fill renderer at 0x0892D56C / 0x0892D5B0.

Separate compositor-group tests showed that one UI group could suppress the visible health-bar layer.

CMain/CGauge analysis then identified CGaugeTcb_t::Draw at 0x0892C124 and CMainTcb_t::Draw at 0x0892BDAC.

This was the conceptual turning point: the HUD was no longer treated as one homogeneous 2D layer.

## 4. Semantic anchoring model

Tekken's logical PSP screen is 480 pixels wide with center x=240.

Once individual HUD families were isolated, three recurring semantic anchors emerged: LEFT for P1/left-owned information, CENTER for neutral/shared information, and RIGHT for P2/right-owned information.

For display aspect A and base B = 16/9:

s = B / A
LEFT x' = s*x
CENTER x' = s*x + 240*(1-s)
RIGHT x' = s*x + 480*(1-s)
width' = s*width

The important discovery was semantic ownership, not any one fixed ratio.

## 5. HP shell and HP fill were separate systems

Frame-dump and runtime experiments showed that the static HP shell/trough and colored fill did not share one owner.

The shell path was associated with the battle main compositor and exact long-shell geometry. The colored fill flowed through the gauge renderer.

Stable gauge ownership fields included a P1/P2 side value and side-specific source X.

The safe implementation copied coordinates into scratch storage instead of repeatedly mutating a persistent gauge object.

Detailed battle ownership: v1.2.0/hud-research.md.

## 6. Side strips and rank badges needed different side classifiers

A shared sprite route contained multiple HUD families.

Side-strip packets carried useful mirrored/orientation information. Rank badges did not reliably use the same side sign.

For ranks, authored X relative to screen center was more reliable: X < 240 means LEFT; X > 240 means RIGHT.

## 7. Round markers and winner glow were different render paths

Persistent round markers could be corrected through the centered rectangle family.

The newly earned marker exposed a separate late submission and a one-pixel P2 boundary case.

The residual winner glow was different again: a rotated THROUGH-mode quad converted by another routine.

That glow required its own narrow hook while still using CENTER semantics.

Detailed record: v1.2.0/winner-orb.md.

## 8. Center timer exposed an ABI problem

The large decimal timer had dedicated owner calls and a separate renderer.

A first wrapper made the timer disappear even though the CENTER transform was correct.

The cause was a missing fifth stack-passed argument. Preserving that argument fixed the renderer.

This established that stack arguments and delay-slot behavior are part of the MIPS hook contract.

Detailed record: v1.2.0/center-timer.md.

## 9. Character names were a classification problem

Character-name rectangles were already passing through the rectangle compositor.

They were de-stretched correctly but initially treated as CENTER-owned.

The research identified a stable name family and changed only its semantic anchoring to LEFT or RIGHT based on authored X.

The top battle-mode header was deliberately excluded because it belonged to another text path.

Detailed record: v1.2.0/side-labels.md.

## 10. Practice and Gold Rush required glyph-path research

Practice infinity was not the normal timer. Practice damage/combo rows and Gold Rush labels were not ordinary rectangle sprites either.

The text research showed that changing horizontal scale only at a late packed-state stage could fix placement while leaving glyph geometry stretched.

Changing scale early fixed glyph geometry but could disturb later placement/state.

The accepted strategy therefore applied de-stretch early enough for Tekken to derive narrower glyph geometry, then synchronized later packed state and applied anchor adjustment only to the intended text families.

Detailed record: v1.2.0/mode-hud.md.

## 11. Module footprint became a functional constraint

A controlled A/B changed only mapped PRX memory size while leaving known-good code payload unchanged.

The larger allocation reproduced replacement-texture regressions.

From then on, the compact one-LOAD 0x0EB0 resident layout became part of correctness.

Artifact evidence: v1.2.0/test-builds.md.

## 12. Fixed-ratio correctness was an intermediate validation stage

Before making the HUD aspect-dynamic, the research first established that the important battle-HUD families could be corrected coherently at the 20:9 test ratio.

Several intermediate builds and checkpoints were used to lock down working fixed-ratio behavior before automatic-aspect changes were introduced.

## 13. Generalizing the HUD equations

Once element ownership and anchoring were understood, the transforms could be expressed in terms of runtime aspect.

Let A be the PPSSPP-reported landscape aspect, B = 16/9, s = B/A, and d = 1-s.

The HP fill also required aspect-derived coefficients derived from the automatic-HUD initializer:

hp_shift = 6.528055667877197 * d
hp_scale = 1.0 + 0.24672749638557434 * d

At 16:9 these reduce to identity. At exact 20:9 they reproduce the previously validated fixed-ratio HP values.

## 14. Missing HP fill during AutoHUD was not an HP-math bug

Several automatic-aspect experiments restored most HUD behavior but lost the colored HP fill.

Different coefficient transports were tried. Eventually the complete known-good gauge behavior was restored while leaving the rest of the automatic-HUD build intact.

The HP fill was still missing, proving the failure was downstream of the gauge transform.

Runtime comparison followed the same HP packet through gauge owner, renderer, lookup, packet builder, shared side/rank hook, stock sprite submission, and renderer return.

The gauge inputs and packet geometry were correct.

The first causal divergence was in a shortened shared side/rank hook. Rejection branches still targeted an old forwarding location, so HP packets fell through instead of reaching the stock sprite submitter.

Restoring the common forwarding jump made the colored fill return.

Detailed investigation: v1.2.0/hp-fill-auto-aspect.md.

## 15. Dynamic HP without text regression

After the downstream HP path was repaired, a startup self-patching attempt proved the dynamic math could work but reused initializer instructions still required by font/text setup.

That caused Practice, Gold Rush, and menu text regressions.

The final design preserved the initializer and changed only HP coefficient transport so the gauge consumed values already being computed dynamically.

This kept the repaired HP path, dynamic geometry, mode-specific text, replacement textures/fonts, and the compact footprint.

## 16. Validation boundary

The final v1.2.0 PRX was tested across Arcade, Story, Ghost Battle, Practice, Gold Rush, HP full/partial states, mode-specific battle text, and replacement textures/fonts.

The implementation derives correction from PPSSPP's runtime-reported aspect.

The release test device was approximately 20:9, so every possible aspect ratio was not independently visually validated.

## 17. Research methodology that proved reliable

1. Start from a known-good control.
2. Change one variable at a time.
3. Distinguish static plausibility from runtime ownership.
4. Use exaggerated diagnostics when subtle changes are ambiguous.
5. Separate element ownership before applying transforms.
6. Preserve MIPS ABI and delay-slot semantics.
7. Keep global render changes away from unrelated overlays.
8. Compare working and broken builds at the same pipeline stage.
9. Follow packets downstream until the first causal divergence.
10. Treat module layout as runtime behavior when A/B evidence proves it.

## 18. Final synthesis

The final AutoHUD implementation came from a narrowing process:

known-good 3D-only baseline -> projection hypotheses -> failed ortho tests -> screen-space/descriptor/native-2D tracing -> battle compositor and gauge ownership -> per-family semantic anchoring -> text/glyph-path correction -> memory-layout constraint -> runtime aspect generalization -> downstream HP packet bug isolation -> dynamic coefficient integration.

The key technical insight is that Tekken 6 does not expose one universal HUD scale.

The successful solution is a composition of narrowly scoped corrections tied to the actual owners of different HUD families, driven by a common aspect model where appropriate.
